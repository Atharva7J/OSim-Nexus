Executive Overview

OSim Nexus is an advanced educational simulation platform designed to demystify the core operational mechanisms of modern Operating Systems. In standard computer science pedagogy, operating systems theory is frequently perceived as excessively abstract. Conceptual models such as non-preemptive versus preemptive CPU scheduling, dynamic contiguous memory compaction, virtual memory page replacement anomalies, mutual exclusion semaphores, deadlock avoidance matrices, and disk-head sweep mechanics are commonly taught through static whiteboard drawings and dry mathematical equations.

When students and junior engineers analyze these systems solely through static formulas, subtle dynamic behaviors—such as convoy effects in FCFS, starvation in priority scheduling, cascading external fragmentation during allocation and deallocation, race conditions in critical sections, and boundary sweeps in disk elevators—are lost. Real hardware operating systems (such as Linux or Windows) schedule threads at microsecond granularities across millions of kernel instructions, rendering live inspection in a classroom setting impractical and opaque.

OSim Nexus solves this fundamental educational dilemma by constructing a deterministic discrete-event simulation laboratory. By decoupling compute logic into an asynchronous Python FastAPI backend and rendering live state transformations through a reactive TypeScript frontend, OSim Nexus exposes the exact internal state of OS algorithms at every logical clock tick.

Core Engineering Philosophy: Strict Textbook Compliance
Every mathematical formula, state transition, and replacement policy in OSim Nexus adheres strictly to the canonical definitions found in Operating System Concepts (Silberschatz, Galvin, and Gagne). Results are 100% deterministic, reproducible, and verifiable via automated pytest suites.

Problem Statement

Traditional computer science curricula face a substantial instructional gap between theoretical OS concepts and observable runtime behavior. Specifically:

● Scheduling Intangibility

Understanding how quantum expiration triggers context switches in Round Robin, or how incoming burst times preempt running tasks in SRTF, requires tracking multiple time-varying variables simultaneously.

● Fragmentation Opacity

Dynamic memory allocation strategies (First Fit, Best Fit, Worst Fit, Next Fit) generate fragmented free blocks whose spatial layout and coalescing behaviors cannot be effectively understood from numerical listings alone.

● Memory & Deadlock Invisibility

Page replacement algorithms (e.g., Bélády's anomaly in FIFO, Clock bit resets, and future-knowledge optimal replacements) and Banker's safety vector math are prone to calculation errors when solved manually by students.

● Concurrency Abstractness

Semaphore state transitions (wait() / signal()) and resource contention in Dining Philosophers or Bounded Buffer systems are difficult to trace without deterministic step-by-step playback.

OSim Nexus directly addresses this educational gap by offering a structured visual sandbox where inputs can be customized, algorithms can be simulated side-by-side on identical workloads, and complete chronological event logs explain why every single decision was made.

CPU Scheduling Engine & Algorithm Analysis

The CPU Scheduler is responsible for deciding which ready process is allocated the central processing unit when the core becomes available. OSim Nexus implements 6 classical scheduling algorithms in backend/app/services/cpu_scheduling.py.

Explain in 30 Seconds

CPU scheduling is like an airport air traffic controller deciding which plane gets the runway. Non-preemptive algorithms let a landed plane taxi until it finishes; preemptive algorithms force a plane to circle or wait if an emergency flight (shorter job or higher priority) suddenly arrives on the radar.

Implemented Scheduling Algorithms

First-Come, First-Served (FCFS)

Principle: Non-preemptive. Processes are dispatched strictly in order of their arrival time ($AT$). The CPU executes each task until completion before picking the next arrived process.

Complexity: Time: $\mathcal{O}(n \log n)$ due to initial arrival sorting; Space: $\mathcal{O}(n)$.

Convoy Effect: If a CPU-bound process with a massive burst time arrives first ($P_1, BT=24$), subsequent short interactive processes ($P_2, BT=3; P_3, BT=3$) are forced to wait, skyrocketing the average waiting time.

OSim Nexus Behavior: If no process has arrived at current time $t$, OSim Nexus logs an EventType.CPU_IDLE event and fast-forwards the clock to the next arrival, appending an IDLE block in the Gantt chart.

Shortest Job First (SJF — Non-Preemptive)

Principle: When the CPU becomes free, the scheduler inspects all arrived processes ($AT \le t$) and dispatches the process with the smallest burst time ($BT$). Once dispatched, it runs to completion.

Provable Optimality: SJF is mathematically provably optimal for minimizing average waiting time among all non-preemptive algorithms.

Limitation: In real operating systems, future CPU burst times cannot be known in advance (must be predicted via exponential smoothing: $\tau_{n+1} = \alpha t_n + (1-\alpha)\tau_n$). Long jobs can suffer starvation if a continuous stream of short jobs arrives.

Complexity: Time: $\mathcal{O}(n^2)$ search or $\mathcal{O}(n \log n)$ with min-heap; Space: $\mathcal{O}(n)$.

Shortest Remaining Time First (SRTF — Preemptive SJF)

Principle: Preemptive version of SJF. Evaluated at each time unit or process arrival. If a new process arrives with a remaining burst time smaller than the currently executing process's remaining time, the running process is preempted and returned to the ready queue.

Trade-off: Achieves even lower average turnaround and waiting times than non-preemptive SJF, but introduces context switch overhead.

Complexity: Time: $\mathcal{O}(n \cdot \sum BT)$; Space: $\mathcal{O}(n)$.

OSim Nexus Implementation: Handled step-by-step in a while completed < n loop. Context switch counts are incremented whenever prev_pid != p.pid.

Round Robin (RR)

Principle: Designed specifically for time-sharing systems. A fixed time slice called a Time Quantum ($q$) is defined. The ready queue is managed as a FIFO circular queue. The scheduler traverses the queue, allocating the CPU to each process for up to $q$ time units.

Quantum Sizing Dilemma:

  • If $q \to \infty$, Round Robin degenerates into FCFS.
  • If $q \to 0$, processor sharing occurs, but context-switching overhead dominates and degrades actual throughput. Rule of thumb: 80% of CPU bursts should be shorter than $q$.

OSim Nexus Queue Management: Uses an explicit Python deque. Arriving processes at time $t$ are appended to the ready queue, followed by the preempted process, guaranteeing textbook-compliant ordering.

Priority Scheduling (Non-Preemptive)

Principle: Each process is assigned an integer priority level. In OSim Nexus, lower numerical value denotes higher priority (standard UNIX nice convention). When the CPU is free, the highest priority arrived process is selected and runs to completion.

Starvation (Indefinite Blocking): A major issue where low-priority processes wait indefinitely if high-priority processes keep arriving. Standard solution: Aging (gradually increasing process priority over time).

Priority Scheduling (Preemptive)

Principle: If an arriving process has a higher priority (smaller numerical integer) than the currently running process, the CPU immediately preempts the running process and dispatches the newly arrived process.

OSim Nexus Implementation: Checked at every discrete time step. Emits EventType.PROCESS_SWITCH with descriptive event metadata describing the priority comparison.

Process Management & Process Control Block (PCB)

In a real operating system, every process is represented by a kernel data structure known as the Process Control Block (PCB). In OSim Nexus, this is implemented as an explicit dataclass in backend/app/services/cpu_scheduling.py: 

@dataclass
class Process:
    """Internal mutable process representation for the scheduling engine."""
    pid: str
    arrival_time: int
    burst_time: int
    priority: int = 0
    remaining_time: int = 0
    start_time: int = -1
    completion_time: int = 0
    waiting_time: int = 0
    response_time: int = -1

    def __post_init__(self):
        self.remaining_time = self.burst_time

When a context switch occurs, the scheduler saves the running task's CPU registers, program counter, and remaining execution time into its PCB, restoring the newly selected task's state. In OSim Nexus, this is modeled by tracking remaining_time, updating start_time on first dispatch, and emitting discrete switch events.

CPU Scheduling Metrics & Mathematical Formulas

The scheduling engine computes 7 standard performance metrics for every simulation run:

Completion Time ($CT$)

The exact time stamp at which process execution terminates.

CT = \text{Time instant of completion}
Turnaround Time ($TAT$)

Total time elapsed between process submission and completion.

TAT = CT - AT
Waiting Time ($WT$)

Total time spent sitting in the ready queue waiting for CPU allocation.

WT = TAT - BT
Response Time ($RT$)

Time from process arrival until its very first CPU execution starts.

RT = \text{Start Time} - AT
CPU Utilization ($\%$)

Fraction of total wall-clock time that the CPU was actively executing user code.

\text{Utilization} = \frac{\sum BT}{\text{Total Time}} \times 100\%
Throughput

Number of processes completed per unit time.

\text{Throughput} = \frac{N}{\text{Total Time}}
Important Distinction: Waiting Time vs. Response Time
In non-preemptive algorithms like FCFS and SJF, Waiting Time == Response Time. However, in preemptive algorithms (Round Robin and SRTF), a process may receive CPU service quickly (low Response Time) but later spend additional cycles in the ready queue after being preempted, making Waiting Time substantially larger.

Paging & Page Replacement Lab

Virtual memory decouples the process's logical address space from physical RAM. The logical address space is divided into fixed-size chunks called Pages, while physical RAM is divided into equal-sized slots called Frames. When a process requests a page not currently mapped to physical memory, a Page Fault interrupt occurs, requiring a frame allocation or victim page eviction.

Explain in 30 Seconds

Page replacement is like a study desk with space for only 3 textbooks (frames). If you need to open a 4th book (page fault), you must choose which book to put back on the bookshelf. FIFO evicts the book placed there longest ago; LRU evicts the book you haven't opened in the longest time; Optimal evicts the book you won't need until next month.

Implemented Page Replacement Algorithms

Algorithm Eviction Policy Hardware / Overhead Requirements Prone to Bélády's Anomaly? Time Complexity
FIFO Evicts the page residing in memory for the longest time. Minimal; single FIFO queue tracking arrival order. YES (documented in tests) $\mathcal{O}(N \times M)$
LRU Evicts the page that has not been referenced for the longest past duration. Requires timestamps or counter stack per frame reference. NO (Stack algorithm) $\mathcal{O}(N \times M)$
Optimal (Bélády) Evicts the page that will not be used for the longest future duration. Theoretical optimum; impossible in real OS without future knowledge. NO (Stack algorithm) $\mathcal{O}(N \times M)$
Second Chance (Clock) Approximates LRU using a 1-bit reference flag and rotating circular pointer. Very low overhead; single reference bit per frame. YES (FIFO variant) $\mathcal{O}(N \times M)$
Bélády's Anomaly
Normally, increasing the number of physical frames reduces page faults. However, with FIFO replacement, certain reference strings (e.g., 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5) result in 9 page faults with 3 frames, but 10 page faults with 4 frames! LRU and Optimal are immune because they belong to the class of stack algorithms, where the set of pages in an $n$-frame memory is always a subset of the pages in an $(n+1)$-frame memory.

Contiguous Memory Management Lab

In variable-partition contiguous allocation, physical memory is treated as a continuous address space divided into allocated process partitions and free blocks (holes). OSim Nexus implements 4 classical dynamic storage allocation strategies in backend/app/services/memory_management.py:

1. First Fit

Scans memory from address 0 and allocates the very first available hole that is large enough ($\text{size} \ge S$). Fast and computationally cheap.

2. Best Fit

Scans all free blocks and allocates the smallest hole that is large enough ($\min (\text{size} - S) \ge 0$). Leaves behind very tiny, unusable slivers of free memory.

3. Worst Fit

Scans all free blocks and allocates the largest available hole ($\max \text{size}$). Produces the largest remaining leftover hole, hoping it remains useful.

4. Next Fit

Variation of First Fit that begins searching from the location of the previous allocation rather than restarting from address 0, dispersing allocations across memory.

Adjacent Hole Coalescing & Fragmentation Formula

When a process deallocates memory, OSim Nexus automatically executes the _merge_free() routine to merge adjacent contiguous free blocks into a single consolidated hole.

\text{External Fragmentation} = 1.0 - \frac{\text{Largest Free Block}}{\text{Total Free Memory}}

If total free memory is 400 KB, but it is split into four 100 KB non-contiguous fragments, the largest free block is only 100 KB. The external fragmentation score is $1.0 - (100 / 400) = 0.75$ (75%), proving that an incoming 150 KB request would fail despite 400 KB of total free space.

Process Synchronization Lab

When concurrent processes share memory or resources, uncontrolled access leads to Race Conditions. To guarantee correctness, concurrent execution must satisfy three critical requirements:

  • Mutual Exclusion: If process $P_i$ is executing in its critical section, no other processes can execute in their critical sections.
  • Progress: If no process is executing in its critical section and some processes wish to enter, only those processes not in their remainder sections can participate in the selection.
  • Bounded Waiting: A bound must exist on the number of times other processes are allowed to enter their critical sections after a process has made a request.

1. Bounded Buffer (Producer-Consumer)

Implemented in OSim Nexus with a fixed buffer capacity of size $N$ using 3 standard counting and binary semaphores:

  • empty: Initialized to $N$ (counts available empty buffer slots).
  • full: Initialized to $0$ (counts occupied buffer slots).
  • mutex: Binary semaphore initialized to $1$ (guarantees mutual exclusion during buffer modification).
Figure 18.1: Bounded Buffer Semaphore Architecture with Capacity Tracking

2. Dining Philosophers Problem

$N$ philosophers sit around a circular table. Between each pair of philosophers sits a single shared fork. To eat, a philosopher requires both their left fork ($i$) and right fork ($(i+1) \pmod N$). OSim Nexus implements a live step-interactive state machine tracking three states:

  • THINKING: The philosopher is contemplating and holds no forks.
  • HUNGRY: The philosopher attempts to pick up forks; if either fork is held by an active neighbor, execution is SYNC_BLOCKED.
  • EATING: Both left and right forks are locked by this philosopher.

Deadlock Management & Banker's Algorithm

A deadlock occurs when a set of processes are blocked because every process holds resources and waits for resources held by other processes in the set. A deadlock can arise if and only if four necessary conditions hold simultaneously:

1. Mutual Exclusion

At least one resource is held in a non-shareable mode.

2. Hold and Wait

A process must be holding at least one resource and requesting additional resources held by others.

3. No Preemption

Resources cannot be forcibly confiscated; they are released only voluntarily.

4. Circular Wait

A closed loop exists: $P_0$ waits for $P_1$, $P_1$ waits for $P_2$, ..., $P_n$ waits for $P_0$.

Banker's Algorithm for Deadlock Avoidance

Banker's algorithm tests for safety by simulating the allocation of predetermined maximum possible amounts of all resources, and then runs an $\mathcal{O}(m \cdot n^2)$ safety check:

\text{Need}[i][j] = \text{Maximum}[i][j] - \text{Allocation}[i][j]

Safety Algorithm Execution Steps:

  1. Let $\text{Work} = \text{Available}$ (vector of length $m$) and $\text{Finish}[i] = \text{False}$ for $i=0..n-1$.
  2. Find an index $i$ such that:
    a) $\text{Finish}[i] == \text{False}$
    b) $\text{Need}[i] \le \text{Work}$
    If no such $i$ exists, skip to Step 4.
  3. $\text{Work} = \text{Work} + \text{Allocation}[i]$, $\text{Finish}[i] = \text{True}$. Append $P_i$ to safe sequence. Go to Step 2.
  4. If $\text{Finish}[i] == \text{True}$ for all $i$, the system is in a SAFE STATE. Otherwise, it is UNSAFE.

Matrix-Based Deadlock Detection

When maximum resource declarations are not known in advance, OSim Nexus runs Deadlock Detection using Allocation, Request, and Available matrices. Any process that cannot fulfill its immediate outstanding request vector from the reclaimed pool is flagged as deadlocked, isolating circular dependency cycles (e.g., $P_0 \leftrightarrow P_1$).

Magnetic disk access time is dominated by Seek Time (the time required to position the read/write head assembly over the target cylinder). OSim Nexus implements 6 classical disk head scheduling algorithms in backend/app/services/disk_scheduling.py:

Algorithm Operational Mechanism Boundary Reversal Behavior Starvation Risk
FCFS Services requests strictly in order of queue arrival. None; follows random queue jumps. None; strictly fair.
SSTF Selects the pending request closest to current head position. Locally greedy; oscillates around cluster. High for peripheral cylinders.
SCAN (Elevator) Moves toward disk edge servicing requests, reverses at end. Always travels to disk boundary (0 or disk_size-1). Low; uniform sweep.
C-SCAN Sweeps in one direction, jumps back to cylinder 0 without servicing. Returns to opposite boundary to provide uniform wait times. Low; even distribution.
LOOK Version of SCAN that reverses as soon as the last request in that direction is served. Does not travel to physical boundary unless a request exists there. Low; more efficient than SCAN.
C-LOOK Version of C-SCAN that jumps only as far as the lowest pending request. Returns only to lowest pending request cylinder. Low; optimal circular seek.

Simulation Engine & Determinism

OSim Nexus uses a Deterministic Discrete-Event Simulation (DES) paradigm. Unlike asynchronous real-time multi-threading—which is subject to hardware race conditions and non-reproducible thread preemption—OSim Nexus simulates time as discrete logical ticks ($t = 0, 1, 2, \dots$).

Given identical inputs, the simulation engine will produce the exact same Gantt chart, metrics, and event log 100% of the time. This determinism is essential for academic grading, automated unit testing, and reliable student self-study.

Q01 OS Fundamentals
What is an Operating System, and what are its two primary abstract roles?
▶
Short Answer An OS is system software managing hardware resources and providing a virtual abstraction layer. Its two main roles are Resource Allocator and Extended Machine (control program).
Deeper Explanation As a Resource Allocator, the OS arbitrates competing requests for CPU, memory, file space, and I/O devices, ensuring fair and efficient utilization. As an Extended Machine, it abstracts away raw hardware complexities (e.g. disk sector registers, interrupt lines) into convenient abstractions like processes, virtual filesystems, and sockets.
OSim Nexus Connection OSim Nexus models both roles: it visualizes resource allocation (CPU scheduling, memory partitions, disk arms) and provides state abstractions via its discrete-event engine.
Q02 OS Fundamentals
What is the distinction between User Mode and Kernel Mode (dual-mode operation)?
▶
Short Answer Dual-mode operation uses a hardware Mode Bit to protect the machine: User Mode executes user code with restricted instructions, while Kernel Mode (privileged mode) has full hardware access.
Deeper Explanation When an unprivileged process requires hardware access (e.g., disk I/O), it triggers a Software Interrupt or System Call (TRAP). Hardware flips the Mode Bit from 1 (User) to 0 (Kernel), executes the trusted kernel handler, and restores User Mode before returning control.
OSim Nexus Connection While OSim Nexus runs in the browser, its API endpoints (/api/*) conceptually simulate the system calls that request kernel interventions (such as memory allocations and process dispatches).
Q03 OS Fundamentals
What is a Context Switch, and why is it considered pure computational overhead?
▶
Short Answer A context switch is saving the CPU state of the currently executing process and loading the state of the next ready process. It is pure overhead because the CPU performs no user work during this time.
Deeper Explanation During a context switch, the OS saves program counters, register sets, and stack pointers into the Process Control Block (PCB), flushes or invalidates TLB caches, and switches memory management page tables. Depending on memory architecture, it takes several microseconds of idle time.
OSim Nexus Connection OSim Nexus explicitly records a context switch counter in SchedulingResult and logs EventType.PROCESS_SWITCH whenever a running PID changes in Round Robin or preemptive priority algorithms.
Q04 OS Fundamentals
What is the difference between a Process and a Thread?
▶
Short Answer A process is an executing program with its own private address space; a thread is the basic unit of CPU execution within a process that shares memory and resources with sibling threads.
Deeper Explanation Processes have independent virtual memory, file descriptors, and security contexts. Threads share the text, data, and heap segments of their parent process but possess their own stack, register set, and program counter. Creating and switching threads is substantially faster than processes.
OSim Nexus Connection OSim Nexus focuses on process-level scheduling and synchronization models, tracking independent PIDs and distinct resource allocation blocks.
Q05 OS Fundamentals
What are the five canonical states of an OS process lifecycle?
▶
Short Answer NEW, READY, RUNNING, WAITING (BLOCKED), and TERMINATED.
Deeper Explanation NEW: process being created; READY: admitted to memory, waiting for CPU assignment; RUNNING: instructions being executed on the CPU; WAITING: waiting for some event or I/O completion; TERMINATED: process has finished execution and OS reclaims its PCB.
OSim Nexus Connection Formally defined in backend/app/models/simulation.py as ProcessState(str, Enum) with states NEW, READY, RUNNING, WAITING, and TERMINATED.
Q06 OS Fundamentals
What is a System Call and how does it differ from a standard library function call?
▶
Short Answer A system call requests privileged kernel service via hardware traps; a library function executes in user space, though it may internally invoke a system call.
Deeper Explanation Calling printf() in C is a user-space library call that formats strings into a buffer and eventually executes the write() system call, switching the CPU to kernel mode to interact with video/tty device drivers.
OSim Nexus Connection In OSim Nexus, the frontend fetch calls to /api/memory/simulate simulate user-space applications requesting kernel memory partitions via brk()/mmap().
Q07 CPU Scheduling
What is the primary difference between preemptive and non-preemptive CPU scheduling?
▶
Short Answer Non-preemptive allows a process to run until it finishes or yields; preemptive allows the OS to forcibly suspend a running task to allocate CPU to another.
Deeper Explanation Non-preemptive algorithms (FCFS, Non-Preemptive Priority, SJF) only switch when a task terminates or enters a waiting state. Preemptive algorithms (Round Robin, SRTF, Preemptive Priority) can interrupt running tasks on timer ticks or higher-priority arrivals, optimizing responsiveness at the cost of context-switching overhead.
OSim Nexus Connection In backend/app/services/cpu_scheduling.py, SRTF and Priority Preemptive evaluate remaining bursts or priority ranks at every discrete time step, emitting EventType.PROCESS_SWITCH when preemption occurs.
Q08 CPU Scheduling
What is the Convoy Effect in First-Come, First-Served (FCFS)?
▶
Short Answer When a long CPU-bound process blocks a series of short I/O-bound processes from getting the CPU, lowering overall device utilization.
Deeper Explanation If P1 with burst 30 arrives first, short processes P2 (burst 2) and P3 (burst 2) wait 30 units before executing. Average waiting time skyrockets, and peripheral devices sit idle waiting for short tasks to finish their CPU bursts.
OSim Nexus Connection Easily simulated in OSim Nexus by configuring P1 with burst 20 and P2..P4 with burst 2. The resulting Gantt chart graphically highlights the idle queue buildup.
Q09 CPU Scheduling
Why is Shortest Job First (SJF) provably optimal for minimizing average waiting time?
▶
Short Answer Because scheduling the shortest job first moves the largest number of processes out of the waiting queue in the minimum total time.
Deeper Explanation Mathematically, each process burst contributes to the waiting time of all subsequent processes. By ordering jobs such that shortest bursts come first, smaller burst values are multiplied across the remaining queue count, minimizing the sum total of waiting times.
OSim Nexus Connection Demonstrated in the Algorithm Lab (/lab): running SJF against any workload consistently produces the lowest average waiting time among all non-preemptive options.
Q10 CPU Scheduling
How does Shortest Remaining Time First (SRTF) differ from non-preemptive SJF?
▶
Short Answer SRTF is the preemptive variant of SJF: if an arriving process has a burst shorter than the remaining burst of the running process, the running process is preempted.
Deeper Explanation SJF evaluates burst times only when the CPU is completely idle. SRTF re-evaluates the ready set upon every new arrival. If a running job has 5 units left and a new job arrives with burst 2, SRTF immediately context-switches to the 2-unit job.
OSim Nexus Connection Implemented in srtf() in cpu_scheduling.py and validated in test_textbook_preemption in test_cpu_scheduling.py.
Q11 CPU Scheduling
How does Time Quantum size affect Round Robin scheduling?
▶
Short Answer A large quantum degenerates RR into FCFS; an excessively small quantum generates severe context-switching overhead that degrades throughput.
Deeper Explanation If quantum q >= max(burst), every process finishes on its first turn, identical to FCFS. If q is 1ms and context switch takes 0.1ms, 10% of CPU time is wasted on dispatch overhead. Textbook rule of thumb: ~80% of CPU bursts should finish within a single quantum.
OSim Nexus Connection OSim Nexus allows real-time adjustment of time_quantum in /cpu. Setting q=1 on burst 8 shows exactly 8 interleaved quantum executions.
Q12 CPU Scheduling
How does Priority Scheduling define priorities, and what is the convention in OSim Nexus?
▶
Short Answer Priorities are integer values representing scheduling precedence. In OSim Nexus (and UNIX), a lower numerical value indicates a higher priority.
Deeper Explanation Priority scheduling dispatches the arrived process with the highest priority rank. In OSim Nexus, priority 0 is higher than priority 3. If multiple processes share the same priority, OSim Nexus breaks ties deterministically using arrival time (FIFO).
OSim Nexus Connection In cpu_scheduling.py: ready.sort(key=lambda p: (p.priority, p.arrival_time, p.pid)).
Q13 CPU Scheduling
What is Starvation (Indefinite Blocking) and how does Aging solve it?
▶
Short Answer Starvation occurs when low-priority processes wait indefinitely due to a continuous influx of high-priority jobs. Aging gradually increases waiting process priorities.
Deeper Explanation In a heavily loaded system, a priority 10 process might never execute if priority 1 and 2 jobs keep arriving. Aging increments a waiting process priority by 1 every fixed time interval (e.g. every 15 minutes) until it reaches priority 0 and executes.
OSim Nexus Connection Documented in Docs.tsx and demonstrated when comparing preemptive priority scheduling against Round Robin in the Algorithm Lab.
Q14 CPU Scheduling
Define Turnaround Time, Waiting Time, and Response Time with formulas.
▶
Short Answer TAT = Completion - Arrival; WT = TAT - Burst; RT = First Scheduled Time - Arrival.
Deeper Explanation Turnaround Time measures total residency in the system. Waiting Time measures pure idle time spent in the ready queue. Response Time measures the latency until the first CPU burst begins, which is critical for interactive systems.
OSim Nexus Connection Computed in _build_result() in cpu_scheduling.py for every process and displayed in the /cpu metrics table.
Q15 Paging & Memory
What is Paging and what are its key components?
▶
Short Answer Paging is a memory management scheme that divides logical address space into fixed-size Pages and physical RAM into equal-sized Frames.
Deeper Explanation Because pages and frames are identical in size, any logical page can be mapped to any physical frame. The Memory Management Unit (MMU) uses a Page Table per process to translate logical addresses (Page Number, Offset) into physical addresses (Frame Number, Offset). Paging completely eliminates external fragmentation.
OSim Nexus Connection Simulated at /paging where users configure the number of physical frames (e.g. 3 or 4) and observe pages mapped into frame slots.
Q16 Paging & Memory
What is a Page Fault and what occurs when one is triggered?
▶
Short Answer A page fault is an MMU hardware trap triggered when a process accesses a page whose valid-invalid bit is marked invalid (not currently resident in RAM).
Deeper Explanation When a page fault occurs: 1) CPU traps to OS kernel, 2) OS verifies page reference validity, 3) Finds a free physical frame (or selects a victim via replacement algorithms), 4) Schedules disk I/O to read page into frame, 5) Updates page table valid bit, 6) Restarts the faulting instruction.
OSim Nexus Connection In backend/app/services/paging.py, each missing page logs EventType.PAGE_FAULT, and if all frames are occupied, triggers EventType.PAGE_REPLACEMENT.
Q17 Paging & Memory
How does First-In, First-Out (FIFO) page replacement operate?
▶
Short Answer FIFO tracks the insertion order of resident pages and evicts the page that has been in physical memory the longest.
Deeper Explanation Managed via a simple FIFO queue. When a frame replacement is needed, the page at the head of the queue is evicted. While simple to implement, FIFO can evict heavily used variable pages simply because they were initialized first.
OSim Nexus Connection Implemented in fifo() in paging.py using a queue tracking insertion sequence.
Q18 Paging & Memory
What is Belady's Anomaly and which algorithms are susceptible to it?
▶
Short Answer Belady's Anomaly is when increasing the number of physical frames results in more page faults. FIFO is susceptible; LRU and Optimal are immune.
Deeper Explanation Under FIFO, reference string 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5 yields 9 page faults with 3 frames, but 10 page faults with 4 frames. Stack algorithms (where pages in n frames are always a subset of n+1 frames) cannot exhibit this anomaly.
OSim Nexus Connection Tested and verified in test_paging.py; documented in Docs.tsx and the Paging module cards.
Q19 Paging & Memory
How does Least Recently Used (LRU) page replacement work?
▶
Short Answer LRU evicts the resident page that has not been referenced for the longest past time interval.
Deeper Explanation LRU relies on the principle of locality of reference (pages used recently will likely be used again soon). It requires hardware assistance like reference timestamps or a doubly-linked stack. It achieves near-optimal fault rates without requiring future knowledge.
OSim Nexus Connection Implemented in lru() in paging.py by maintaining a last_used: dict[int, int] tracking the most recent step index for each resident page.
Q20 Paging & Memory
What is the Optimal (Belady's / MIN) page replacement algorithm?
▶
Short Answer Optimal evicts the page that will not be used for the longest future duration. It is physically unrealizable but acts as a benchmark.
Deeper Explanation Optimal inspects the future reference string and identifies which currently resident page is referenced farthest away (or never again). It is mathematically guaranteed to achieve the lowest possible page fault count for any given frame size.
OSim Nexus Connection Implemented in optimal() in paging.py by searching reference_string[step + 1:] for the maximum forward index.
Q21 Paging & Memory
How does the Second Chance (Clock) page replacement algorithm approximate LRU?
▶
Short Answer It uses a circular queue of frames with a 1-bit reference flag; when searching for a victim, it gives pages with bit=1 a second chance (clearing the bit to 0) before evicting a page with bit=0.
Deeper Explanation The clock hand points to the next candidate. If reference bit is 0, the page is evicted. If 1, the bit is cleared to 0, the hand advances, and the search continues circularly. This achieves performance close to LRU with minimal hardware overhead (only 1 bit per frame).
OSim Nexus Connection Implemented in second_chance() in paging.py and verified in test_paging.py.
Q22 Paging & Memory
Define Hit Ratio and Fault Ratio with their formulas.
▶
Short Answer Hit Ratio = Hits / Total References; Fault Ratio = Faults / Total References. Their sum always equals 1.0 (100%).
Deeper Explanation Hit Ratio measures cache/memory efficiency. If a reference string has 20 accesses with 8 hits and 12 faults, Hit Ratio = 8/20 = 0.40 (40%), and Fault Ratio = 12/20 = 0.60 (60%).
OSim Nexus Connection Calculated in all paging algorithms and rendered with progress bars and badges at /paging.
Q23 Memory Management
Explain First Fit, Best Fit, and Worst Fit allocation strategies.
▶
Short Answer First Fit picks the first hole that fits; Best Fit picks the smallest hole that fits; Worst Fit picks the largest available hole.
Deeper Explanation First Fit is fastest. Best Fit minimizes wasted space per block but leaves behind tiny unusable hole slivers. Worst Fit produces the largest remaining leftover hole, hoping it can satisfy subsequent allocations.

Q24 Memory Management
How does Next Fit differ from First Fit?
▶
Short Answer Next Fit begins searching for a free hole from the location of the previous allocation rather than starting from address 0.
Deeper Explanation First Fit tends to concentrate small holes at the start of memory. Next Fit distributes allocations circularly across the entire memory space, but can fragment the end of memory faster.

Q25 Memory Management
What is External Fragmentation and what formula does OSim Nexus use to quantify it?
▶
Short Answer External fragmentation is total free memory broken into non-contiguous holes too small to satisfy requests. Formula: 1.0 - (Largest Hole / Total Free Memory).
Deeper Explanation If total free memory is 500 KB but the largest single block is only 100 KB, a 150 KB allocation fails. External fragmentation = 1.0 - (100 / 500) = 0.80 (80%).
OSim Nexus Connection Computed in MemoryManager.get_state() and displayed in the live /memory metric card.
Q26 Memory Management
What is Memory Compaction and why is it expensive?
▶
Short Answer Compaction is moving all allocated partitions to one end of memory to consolidate all free holes into one large block. It is expensive due to heavy memory copying.
Deeper Explanation Compaction requires relocatable dynamic binding (base and limit registers). Moving megabytes or gigabytes of memory freezes running processes and consumes significant memory bus bandwidth.
OSim Nexus Connection OSim Nexus demonstrates how coalescing upon deallocation helps mitigate the need for full compaction.
Q27 Memory Management
What is the 50-Percent Rule in contiguous memory allocation?
▶
Short Answer For every N allocated blocks, statistical analysis shows that approximately 0.5 N blocks are lost to fragmentation.
Deeper Explanation Discovered by Knuth: in equilibrium with First Fit, approximately one third of memory is trapped in unusable holes due to fragmentation, meaning 50% as many blocks as allocated blocks are free holes.
OSim Nexus Connection Observed when running sequences of allocate/deallocate operations at /memory.

Why does paging eliminate external fragmentation entirely?
▶
Short Answer Because memory is allocated in fixed-size frames, allowing any logical page to be placed in any non-contiguous free frame.
Deeper Explanation Since all pages and frames are identical in size (typically 4 KB), there are no variable-sized partitions between processes. Any free frame can satisfy any page request, so free memory never becomes unusable due to size mismatches.

What is a Race Condition and what is a Critical Section?

Deeper Explanation If thread A reads count=5 and is interrupted before writing count+1, and thread B reads count=5 and writes 6, the first increment is lost. Protecting the critical section with mutual exclusion prevents race conditions.

How do wait() (P) and signal() (V) semaphore operations operate?

Q40 Deadlock
Walk through the safety verification steps of Banker's Algorithm.
▶
Short Answer 1. Work = Available, Finish = [False]*N. 2. Find process i where Finish[i]==False and Need[i] <= Work. 3. Work += Allocation[i], Finish[i]=True, append Pi. 4. If all finish, SAFE.
Deeper Explanation The algorithm simulates the execution of processes that can currently finish. When process i finishes, it releases all allocated resources back to the Work pool, enabling subsequent processes with larger needs to execute.

▶
Short Answer To provide uniform waiting times across all cylinders by servicing requests in only one direction.
Deeper Explanation Under SCAN, cylinders near the boundary are serviced twice in rapid succession (outward and immediately inward), while cylinders at the opposite edge wait the longest. C-SCAN eliminates this bias by jumping back to cylinder 0 without servicing on the return trip.

Limitations & Academic Boundaries

In the interest of academic integrity, the following architectural boundaries are explicitly documented:

  • Educational Simulation, Not a Real Kernel: OSim Nexus simulates algorithms mathematically; it does not dispatch real operating system kernel threads or interface with physical x86/ARM hardware registers.
  • Single-Machine Execution: It models single-processor and classical single-disk architectures; it does not model distributed clusters, NUMA architectures, or SSD flash translation layers (FTL).
  • Deterministic Concurrency: Process synchronization is simulated via discrete state machine steps rather than real multi-threaded POSIX pthreads, avoiding non-deterministic race conditions during classroom instruction.

Alphabetical Technical Glossary

Term Formal Academic Definition
Arrival Time ($AT$) The discrete time stamp at which a process enters the ready queue and becomes eligible for CPU scheduling.
Banker's Algorithm A deadlock avoidance algorithm developed by Edsger Dijkstra that tests for safe states before allocating resources.
Bélády's Anomaly The counterintuitive phenomenon wherein allocating more physical memory frames increases the total number of page faults under FIFO.
Burst Time ($BT$) The amount of CPU execution time required by a process to complete its current computing phase.
Context Switch The operational procedure of saving the CPU register state of a running process into its PCB and loading the saved state of another process.
External Fragmentation A condition where total available free memory exceeds a process's allocation request, but memory is divided into scattered, non-contiguous holes.
Gantt Chart A horizontal bar chart visualizing the chronological timeline of process allocations on a CPU.
Internal Fragmentation Wasted memory occurring within an allocated partition when the allocated block size exceeds the process's actual memory requirement.
Mutex A binary mutual exclusion lock used to serialize access to a shared critical section.
Page Fault A hardware trap raised by the Memory Management Unit (MMU) when a program accesses a virtual page that is not currently mapped into physical RAM.
Process Control Block (PCB) A kernel data structure containing complete execution context for a process, including PID, state, registers, and memory bounds.
Safe Sequence An ordering of processes $\langle P_1, P_2, \dots, P_n \rangle$ such that for each $P_i$, the resources it can still request can be satisfied by current available resources plus resources held by all preceding processes.
Seek Time The mechanical duration required for a magnetic disk drive's read/write head assembly to traverse to the target cylinder track.
Throughput The rate of work completion, defined as the number of processes successfully completed per unit of simulation time.
Turnaround Time ($TAT$) The total elapsed time from the moment a process arrives in the system until its execution completes ($TAT = CT - AT$).
Waiting Time ($WT$) The total cumulative time a process spends waiting in the ready queue without CPU service ($WT = TAT - BT$).
